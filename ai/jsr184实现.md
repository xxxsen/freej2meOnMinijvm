# JSR184 / M3G 实现说明

## 目标

- 在 `d:\github\j2me\freej2me` 中提供 `javax.microedition.m3g.*` 的 JSR184 API 层与基础语义，可以运行在标准j2se环境中。
- 在 `d:\github\j2me\freej2meOnMinijvm` 中承载运行环境与后续专用实现层，最终跑在 `miniJVM` 上。
- 参考 JSR184 官方文档与 Android 版实现语义，但不照搬 Android JNI 的 `native handle` 设计。
- 先打通“可调用、可校验、可最小渲染”的链路，再继续推进真正的 `GL` backend 与 `.m3g` 资源加载。
- 完善过程中，要把进度及已实现内容记录下来，放在本文件中，方便后续查看与调试。

## 架构原则

- `freej2me` 放标准 API 与通用语义，不引入 Android 风格的 native 句柄层。
- `freej2meOnMinijvm` 负责运行时适配、图形输出链路，以及后续的 `miniJVM + org.mini.gl.GL` backend。
- 平台策略进一步明确为：
  - `freej2me + J2SE` 侧优先保证 API、语义链路和 backend 抽象完整
  - 若 `Graphics3D` 软件渲染上某些严格语义实现会带来明显性能代价，可先保留最小可用或延后到 GL backend
  - `freej2me + miniJVM + OpenGLES` 侧尽可能做完整实现，逐步把高成本语义下沉到 GL backend
  - 因此抽象层与状态表达要尽量完整，避免后续迁移到 OpenGLES 时再返工上层 API
- 第一阶段优先补齐:
  - 数学基础
  - 变换/顶点/索引/相机/纹理等数据结构
  - `Graphics3D` 的状态机、参数校验和最小渲染入口
- 第二阶段再推进:
  - 真正的 GL backend
  - `Loader.load(...)`
  - 更完整的光照、雾、材质、动画、裁剪与兼容性

### backend 抽象当前状态

- `freej2me` 中的 `Graphics3D` 已增加 backend SPI:
  - `Graphics3D.Backend`
  - `Graphics3D.BackendFactory`
  - 默认 `SoftwareRenderBackend`
- `J2SE` 当前继续固定走软件渲染，不需要额外硬件库
- `miniJVM` 当前会优先尝试反射加载:
  - `javax.microedition.m3g.MiniJvmGraphics3DFactory`
- `freej2meOnMinijvm` 已新增第一版 `MiniJvmGraphics3DFactory`
- 当前这版 `MiniJvmGlBackend` 已不再只是空骨架，而是具备第一批真实 GL 提交能力:
  - 通过 `GForm.addCmd(...)` 切回 OpenGL 线程执行
  - 在 `releaseTarget()` 时统一提交一帧
  - 使用 `GLFrameBuffer` 做离屏 FBO
  - 使用 shader + VBO/VAO 绘制三角形
  - 当前会把 FBO 结果读回目标 `BufferedImage` / `Image2D`
- 当前已落地的第一批 GL 子集:
  - `Mesh`
  - `SkinnedMesh` 的最小 GPU 蒙皮通路
  - `Sprite3D` 的当前实现会先转成临时 textured quad，再复用现有 GL 提交链
  - `TriangleStripArray`
  - 顶点位置
  - 顶点色 / `defaultColor`
  - `texCoords(0)`
  - `texCoords(1)` 的 backend 数据通路
  - `Camera`
  - `Background.color`
  - `Background.image`
  - `PolygonMode` 的 cull / winding / flat-vs-smooth 基础行为
  - `CompositingMode` 的 `ALPHA / ALPHA_ADD / MODULATE / MODULATE_X2 / REPLACE`
  - `alphaThreshold`
  - `depthTest / depthWrite / colorWrite / alphaWrite`
  - `depthOffset`
  - `Fog.LINEAR / Fog.EXPONENTIAL` 的基础 shader 混合
  - “无纹理 + 有法线 + 有 `Material` + 有灯光”网格的最小逐顶点光照
    - 当前已接入 `AMBIENT / DIRECTIONAL / OMNI / SPOT`
    - 当前沿用 `freej2me` 软件后端的 CPU 侧世界空间光照计算，再复用现有 GL 纹理/雾提交流程
  - `Texture2D` 的 `RGB/RGBA` 纹理上传与采样
  - `Texture2D` 的 `WRAP_REPEAT / WRAP_CLAMP`
  - `Texture2D` 的 `FUNC_REPLACE / FUNC_MODULATE / FUNC_ADD / FUNC_BLEND / FUNC_DECAL`
  - `Texture2D` 的基础 transform（沿用 `Transformable` 的 composite transform）
  - 最多 2 个 texture unit 的顺序组合:
    - 当前在 shader 中按 `unit 0 -> unit 1` 依次应用纹理函数
    - 每个 unit 可独立携带各自的 texcoord、wrap、blendColor 与 texture transform
  - `MorphingMesh` 走现有 CPU morph 后再送入 GL backend
  - `SkinnedMesh` 在满足约束时走 shader 顶点蒙皮:
    - 当前骨骼 uniform 上限为 `24`
    - 当前 GPU 打包按每顶点最多 `4` 个 influence 输出
    - 若超出当前 GL 子集能力，仍回退到 CPU 蒙皮后的常规 GL/软件路径
- 当前仍未进入 GL 路径、会整帧回退软件 backend 的情况:
  - 非 `RGB/RGBA` 的 `Image2D`
  - 当前 GL 子集未覆盖的 `Fog` 模式
  - 未先 `clear(...)` 就直接在旧目标内容上叠加的场景
- 当前这版的定位仍是“先把 GL 提交链跑通”，不是最终形态:
  - 先保留回读到 `BufferedImage`，确保与当前 2D/AWT 组合链兼容
  - 后续再继续减少回读，逐步转向更直接的 miniJVM GL 显示路径

### MorphingMesh 当前能力

- `MorphingMesh` 构造、`getMorphTarget(...)`、`getMorphTargetCount()`、`setWeights(...)`、`getWeights(...)` 已补齐基础行为
- `Object3D.animate(...)` 已接入 `AnimationTrack.MORPH_WEIGHTS`
- 当前渲染链会在绘制前按 `R = B + sum[w_i * (T_i - B)]` 计算临时顶点数据
- 当前已覆盖的 morph 属性包括:
  - positions
  - normals
  - colors
  - `texCoords(0)`
  - `VertexBuffer.defaultColor`
- 当前实现遵循的关键语义:
  - morph target 为空/数量不一致时做基础参数校验
  - morph target 的 scale/bias 继续忽略，沿用 base mesh 的 scale/bias
  - base 与 target 的数组结构不兼容时，在实际渲染阶段抛出 `IllegalStateException`

### SkinnedMesh 当前能力

- 补齐了骨骼权重及顶点影响的管理语义：
  - 支持 `addTransform(...)` 添加骨骼节点及顶点影响范围与权重。
  - 支持 `getBoneTransform(...)` 与 `getBoneVertices(...)` 查询骨骼信息。
  - 构造时校验 `skeleton` 节点的合法性并建立父子关联。
- 已接入 `Graphics3D` 的渲染链路：
  - 在渲染前会根据每个骨骼的当前变换矩阵及归一化权重，动态计算蒙皮后的临时顶点和法线数据。
- 本轮已确认并处理过一轮 `J2SE` 回归：
  - 在推进骨骼缓存与抽象 GPU 蒙皮过程中，`SkinnedMesh` 一度出现姿态错误。
  - 目前已通过回退到已知正确的 `SkinnedMesh.java / Graphics3D.java` 基线，恢复 `J2SE` 与 `miniJVM` 的 CPU 蒙皮正确性。
- 当前 CPU 蒙皮状态：
  - 继续保留当前已验证正确的临时顶点/法线输出逻辑，作为 `J2SE` 基准路径。
  - 新增的 GPU 蒙皮适配不再直接改动 CPU 主路径，避免再次引入姿态回归。
- 当前 `miniJVM` GPU 蒙皮适配状态：
  - 已补回 `GpuSkinningData` 导出接口，以及 `Graphics3D -> backend` 的 `SkinnedMesh` 直通分支。
  - GPU 导出路径当前会为每个顶点保留前 `4` 个最高权重骨骼并重新归一化，只影响 GPU 打包数据，不影响 CPU 蒙皮结果。
  - 已补充 `MiniJvmGlBackend.renderSkinned(...)` 的拒绝原因日志，用于定位 `gpuSkinnedItems=0` 时是 `flatShading / tooManyLights / tooManyBones / skinningDataUnavailable` 中的哪一种。

## 当前限制

- `miniJVM` 已接入 `org.mini.gl.GL` backend，但当前仍是“先录制一帧 -> 切回 GL 线程 -> FBO 绘制 -> 回读到 `BufferedImage/Image2D`”的过渡形态，还不是最终直显路径。
- `.m3g` loader 现已能反序列化主链对象，但仍未完成全部对象类型与全部严格语义。
- `SPLINE / SQUAD` 仍未按完整规范实现，目前仍是简化语义。
- 近远裁剪、完整透视正确纹理映射、更完整的材质/灯光/雾语义还没完成；当前 `J2SE` 软件路径已补到 `AMBIENT / DIRECTIONAL / OMNI / SPOT` 的基础逐顶点光照、基础 `SPECULAR` 与 `Fog`，但距离完整规范仍有差距。
- `Loader` 的后续大块仍包括:
  - `SkinnedMesh` in-file object 的更完整装载与严格边界语义
  - 其余未覆盖的序列化对象类型
  - 更严格的合法性校验与边界行为
- `Group.pick(...) / RayIntersection` 当前已接入最小可用实现：
  - 已支持 `Mesh` 的 3D pick 与基于 `Camera` 的 2D pick
  - 已支持 `scaled Sprite3D` 的基于 `Camera` 的 2D pick
  - 已填充 `RayIntersection` 的 `distance / submesh / ray / normal / texcoord(0)`
  - 已考虑 `scope`、`PolygonMode` 的 cull/winding，以及 `MorphingMesh` / `SkinnedMesh` 的当前顶点结果
  - `Sprite3D` picking 当前已补入最小 alpha test 与 crop 采样路径；更严格边界语义后续再收口
- `Node.align(...)` 当前已接入最小可用实现：
  - 已支持对当前节点及其 descendants 递归应用 alignment
  - 已支持 `Y/Z` 单轴与双轴对齐
  - 已支持 `ORIGIN / X_AXIS / Y_AXIS / Z_AXIS` 目标
  - 已接入对引用节点、scene graph 路径、自引用/后代引用的基本校验
  - 当前在 `J2SE` 软路径里保守保留平移与轴长度，不做高成本的完整 `M/S/R` 分解
- 多 texture unit / 多套 texcoord 当前已推进到“抽象与数据链路可用”：
  - `Appearance` 已支持 2 个 `Texture2D` 槽位
  - `VertexBuffer` 已支持 2 套 texcoord
  - `Loader` 已可装载最多 2 个 appearance texture unit 与 2 套 texcoord array
  - `Object3D.getReferences()`、`Graphics3D.getProperties().numTextureUnits`、`RayIntersection` 已同步到 2 个单元
  - 当前 `J2SE` 软件渲染仍主用 `unit 0`，不在 software rasterizer 中继续引入高成本逐像素多纹理混合
  - 本轮已把 `miniJVM` 的 GL backend 扩到 2 个 texture unit / 2 套 texcoord：
    - 顶点格式、shader uniform、纹理上传与 appearance 状态都已同步到 `unit 0/1`
    - 当前按顺序串联两个 unit 的基础纹理函数，优先承载后续 `OpenGLES` 侧更完整语义
    - 若遇到当前 GL 子集未覆盖的语义，仍保持整帧 software fallback
    - 本轮已把“无纹理 + 有法线 + 有 `Material` + 有灯光”这条最小逐顶点光照主链接入 GL backend
    - 本轮继续去掉了“带纹理的受光材质网格”与“缺法线但依赖 `Material + Light`”这两类整帧 software fallback
    - 当前在 GL 路径中的策略是：有法线时继续做 CPU 顶点光照；缺法线时退化为不打光但仍尽量保留 GL 提交
    - `Fog.LINEAR / EXPONENTIAL` 已接入当前 shader；若后续再出现其它未覆盖雾语义，仍可继续 fallback
- `Appearance`、`Material`、`PolygonMode`、`CompositingMode`、`Light`、`World` 等类目前仍是“够当前阶段使用”的实现，不是最终完整兼容版。

## 面向 miniJVM GPU 顶点蒙皮的当前判断与后续方案

### 当前进度复核

- `Graphics3D -> SkinningBackend -> MiniJvmGlBackend.renderSkinned(...)` 这条直通链已经接好，`SkinnedMesh` 在满足当前 GL 子集约束时，已能不经 CPU 主渲染路径而直接进入 shader 顶点蒙皮分支。
- `SkinnedMesh.getGpuSkinningData(4)` 已改为“仅在 GPU 导出数据中裁剪到每顶点前 `4` 个最高权重骨骼并重新归一化”，不再因为单个顶点 influence 超过 `4` 就让整件网格完全退出 GPU 路径。
- 当前 shader 蒙皮约束仍是：
  - 每顶点最多 `4` 个 influence
  - 当前骨骼 uniform 上限 `24`
  - 灯光上限 `4`
  - `flat shading`、超骨骼数、超灯光数或拿不到 `GpuSkinningData` 时仍回退
- 当前 `miniJVM GL` 路径的真实性能瓶颈，已不是“只有软件渲染”，而是以下几段叠加：
  - `releaseTarget()` 中切回 GL 线程并同步等待
  - `renderFrame()` 内每帧构造/上传顶点数据
  - `glReadPixels(...)`
  - 回写到 `BufferedImage/Image2D`
- 因此，GPU 顶点蒙皮是必要方向，但单靠“把骨骼矩阵放到 shader”还不够；若回读链路和每帧 CPU 打包仍保留，帧时间依然会偏高。
- 当前文档与代码核对后的结论应表述为：
  - “GPU 顶点蒙皮通路已接入”
  - “top4 influence 导出已实现”
  - “当前样例上已确认命中 GPU 蒙皮，且用户已确认画面位置恢复正常”

### 后续方案

- 第一阶段先做“命中确认”，避免继续在错误前提上优化：
  - 重新运行 retained-mode 样例
  - 确认日志里 `gpuSkinnedItems > 0`
  - 同时记录 `renderSkinned` 拒绝原因、`queueWaitMs / glRunMs / readPixelsMs / copyToTargetMs`
- 第二阶段优先压缩“GPU 蒙皮路径里仍留在 CPU 上的工作”：
  - 尽量缓存 `TriangleStripArray -> triangle list` 展开结果，避免每帧重复展开相同拓扑
  - 尽量缓存与 mesh 拓扑无关的顶点属性布局，减少每帧重复打包大块 `float[]`
  - 保持骨骼矩阵与少量动态 uniform 每帧更新，但把静态数据尽可能变成一次上传、多帧复用
- 第三阶段处理当前更大的公共瓶颈，也就是回读链路：
  - 复用 `readBack` 临时缓冲，避免每帧新建大块 `byte[]`

- 第四阶段再继续扩大 GPU 覆盖面，减少回退概率：
  - 把当前仍在 CPU 侧做的部分顶点光照逐步迁到 shader
  - 在保证正确性的前提下，放宽 `SkinnedMesh` 的可渲染子集约束
  - 继续补齐 `CompositingMode`、`Background.image`、多纹理等在 retained-mode 样例里常命中的路径

### 当前建议的执行顺序

- 先验证 `gpuSkinnedItems > 0` 是否已经稳定命中；若仍为 `0`，先只修 GPU 蒙皮准入，不分散到其它渲染语义。
- 当前样例既然已经确认 GPU 蒙皮命中，就立刻转向减少每帧 CPU 打包与回读；这两项比继续扩大骨骼/灯光上限更影响当前帧时间。

### 回读优化最新进展

- 当前 `MiniJvmGraphics3DFactory.readBack(...)` 已先落地一版更保守的 `A -> B` 优化顺序：
  - `A`：先不改 `glReadPixels(...)` 输出格式，只去掉 `BufferedImage` 目标上的逐像素 `setPixel/setRGB`，改为直接写 `BufferedImage -> ImageMutable` 底层字节缓冲。
  - `A`：同时复用 `readBack` 临时 `byte[]`，避免每帧重新分配整块 RGBA 缓冲。
  - `A`：`Image2D.RGBA` 目标已改为按行 `System.arraycopy(...)` 回写，避免逐像素 Java 循环。
- 在 `A` 的基础上，当前又接入了第一版 `B`：
  - 对 `BufferedImage/ImageMutable(ABGR/BGRA 字节布局)` 目标，在非 `OpenGL ES` 环境下优先尝试 `glReadPixels(..., GL_BGRA, GL_UNSIGNED_BYTE, ...)`
  - 这样回读后的行数据已接近 2D 底层缓冲格式，CPU 端只需做按行翻转与 `System.arraycopy(...)`
  - `opaque` 目标只额外把 alpha 通道统一改成 `0xFF`
- 当前 `B` 的边界刻意保持保守：
  - 由于当前平台实测出现红蓝通道对调，`GL_BGRA` 直读现阶段改为“实验开关”，默认关闭
  - 只有显式设置系统属性 `freej2me.m3g.readback.bgra=true` 时，才在非 `OpenGL ES` 环境启用
  - 在 `OpenGL ES`/未知平台上仍保留 `GL_RGBA` 回读 + Java 端字节重排的安全回退
- 这意味着当前阶段的收益重点已经从“省掉几次位运算”转成：
  - 去掉 `BufferedImage.setRGB(...)` / `target.setPixel(...)` 的逐像素调用开销
  - 把 copy path 尽可能收敛为“行翻转 + 批量拷贝”
- 下一步若还要继续压缩 `copyToTargetMs`，建议顺序是：
  - 先实测桌面 GL 下 `GL_BGRA` 直读后的真实耗时收益
  - 再评估 `OpenGL ES` 上是否存在稳定可用的 `BGRA` 读回能力
  - 若 GLES 平台不稳，再考虑两条更重的路线：专用 JNI bulk copy/swap，或最终 pass 先在 GPU 上完成 swizzle/flip

## 本轮修复：`Graphics3D.render(Node, Transform)` 根节点 local transform 误叠加（Tower Bloxx 塔偏右）

### 现象
- Tower Bloxx 进入演示阶段，镜头从塔底攀升到塔顶，塔身明显偏向屏幕右侧（只能看到半边塔），而广场/围墙位置正确。
- 塔身每隔约 10 层出现一层高的空隙，且塔顶在镜头爬升后消失。
- 标准实现上塔坐落在广场正中、各层连续、塔顶可见。
- 该问题在 `freej2me + J2SE` 与 `freej2me + miniJVM` 上都存在，属共享核心 bug。

### 根因
`Graphics3D.render(Node, Transform)` 的最终世界→相机变换，freej2me 之前是：
```
final = viewTransform × transform参数 × node.local
```
但 JSR-184 参考实现（`J2ME-Loader` 的 C 层 `m3gRenderNode` / `Mesh.setupRender`）是：
```
final = viewTransform × transform参数       // 根节点自己的 local/composite 不参与
```
参考实现证据：
- `m3g_rendercontext.c` `m3gRenderNode`：`s.toCamera = ctx->viewTransform × transform`，只乘 render 的 transform 参数。
- `m3g_mesh.c` `Mesh.setupRender`：`m3gQueueMesh(mesh, &s->toCamera, ...)`，直接用 `s.toCamera`，不再乘 mesh 自身的 composite。
- 只有在场景树**遍历子节点**时（`m3g_group.c`），子节点的 composite 才以 `child.toCamera = parent.toCamera × child.composite` 形式累加。

也就是说：`render(Node, Transform)` 把传入的 Node 当作“根”，transform 参数是它的父变换，**根节点自身的 local 不再叠加**；只有它的后代节点在遍历中各自累加 composite。

### 为什么只有 Tower 受影响
- 广场/围墙用 `render(node, null)` 且 mesh local 为 identity → 不受影响（tx=0）。
- 塔楼层用 `render(mesh, T)`，但塔 mesh 的 local 残留了上一次的变换（`h.b()` 把 Transform 提交到 mesh local 后未清零），典型残留值 `tx=498.2`，每 10 层特殊层 `tx=1906`。freej2me 把这个残留 local 错误地乘了上去，导致塔被推偏、每 10 层特殊层脱节产生空隙、塔顶因 tx 累积过大而消失。
- 其他 3D 游戏用 `render(World)`，world 子节点的 local 本就该应用，所以不受影响。

### 定位手段（已沉淀为通用工具，保留在代码中）
- `BytecodeInjectionTool`（`org.recompile.mobile`）：运行时对第三方 MIDlet 字节码注入。规则格式：
  - `ENTRY_PRINT|<类>|<方法>|<方法描述符>|<模板>`
  - `EXIT_PRINT|<类>|<方法>|<方法描述符>|<模板>`
  - 模板支持 `{n}`（第 n 个参数）与 `{n[m]}`（第 n 个参数是数组时取第 m 个元素）。EXIT_PRINT 在每个 RETURN 前注入，可打印被方法改过的参数。
  - 规则来源：`-Dfreej2me.bytecode.injection.rules`、`-Dfreej2me.bytecode.injection.file`、MIDlet jar 同目录 `<jar>.inject.txt` 或 `freej2me-injections.txt`。
- `Graphics3D` 内置受 `-Dfreej2me.diag.render` 开关控制的渲染诊断：对每个被渲染的 Mesh 打印视口与根节点变换平移量。
- 本轮用注入抓取了 Tower 演示阶段 537 帧真实相机参数（`q.a(FFFFFFFFF)V`），并用真实参数数值验证塔几何本身始终居中（24 帧×6 高度全部 screenX=120），从而排除了相机/投影/矩阵数学，把问题锁定到 render 的节点变换叠加语义。

### 修复（`Graphics3D.java`）
1. `render(Node, Transform)`：根节点不再乘自己的 local，直接用 transform 参数作为该节点的完整父变换（对齐参考实现）。
2. 抽出内部遍历 `renderNodeWithTransform(Node, combined)`：Group 子节点仍各自累加 composite，保留场景树语义。
3. `render(World)`：改为内部遍历，world 子节点的 local 照常应用，避免 `render(World)` 游戏（skaterboy / pogoroo / swerve 等）回归。

修复后 Tower 塔身居中、各层连续、塔顶可见，且 `render(World)` 路径不回归。

### 仍遗留（待后续排查）
- Tower Bloxx 进入游戏后，广场中央多出一个本不该出现的“降落伞小人”，且玩家扔下第 2 层塔后天上飘下来的降落伞小人在“钻进塔”的最后位置停住不消失。怀疑与广场上多出的那个是同一类问题。运行环境 `freej2me + J2SE`。

## 本轮修复：`Node.scope` 可见性检查缺失（Tower Bloxx 降落伞小人不消失）

### 现象
- Tower Bloxx 进入游戏后，广场中央本不该出现却多出一个降落伞小人，且一直不消失。
- 玩家扔下塔层后天上飘下来的降落伞小人，在“钻进塔”的最后位置停住、不再消失；多搭几层后，之前最高层处的伞人仍挂在天空（楼层倒塌、摄像机下移后尤其明显）。
- 标准实现上这些伞人正常消失。运行环境 `freej2me + J2SE`（与 miniJVM 同属共享核心）。

### 根因
游戏隐藏节点的方式是 `Node.setScope(0)`（`h.java` 的 `h.c()`）。JSR-184 规范规定：节点只有在 `(node.scope & camera.scope) != 0` 时才被渲染；`scope=0` 时与任何 scope 按位与均为 0，应不可见。

参考实现（J2ME-Loader C 层 `m3gRenderNode` / `m3g_sprite.c` 的 `setupRender`）有此检查：
```c
if ((self->scope & renderQueue->scope) != 0)   // 才进入渲染队列
```

而 **freej2me 的 `Graphics3D.renderNodeWithTransform` 完全没有检查 scope**，把 scope 仅作为参数向下传但从不据此跳过。结果 `setScope(0)` 的节点仍被渲染 → 伞人该隐藏时不消失。

### 定位过程
- 通过染色诊断（`-Dfreej2me.diag.tint=1`，按顶点数染纯色）确认伞人由 `verts=54`（伞盖）+ `verts=126`/`verts=100`（身体）组成。
- 通过在 `renderTriangleStripsWithSoftwareBackend` 打印 mesh identity hash + transform + 调用栈，发现伞人渲染路径为：
  `i.paint → DCHouseDeluxe.a → c.a → r.a → k.a → k.e(o) → q.b() → Graphics3D.render(Node, null) → Group 遍历 → 渲染伞人 mesh`。
  即伞人是 root Group 的子节点，通过 `render(Node, Transform)` 路径渲染。
- 游戏隐藏伞人的 `h.c()` 调用 `Node.setScope(0)`，而 freej2me 未据此跳过渲染 → 根因锁定为 scope 检查缺失。

### 修复（`Graphics3D.java` `renderNodeWithTransform`）
在遍历开头加入 JSR-184 的 scope 可见性检查：
```java
if (camera != null && (node.getScope() & camera.getScope()) == 0) {
    return;   // scope 无交集，跳过（隐藏）
}
```
默认 scope 为 -1（全位为 1），`-1 & -1 = -1 != 0`，因此普通节点不受影响；只有显式 `setScope(0)` 隐藏的节点才跳过。不影响 skaterboy / pogoroo / swerve 等正常游戏。

### 诊断工具（本轮沉淀，已保留在代码中，受开关控制）
- `BytecodeInjectionTool` 的 `EXIT_PRINT` 规则扩展支持 `{ret}`：在方法返回前打印返回值（DUP 栈顶值）。
- `Graphics3D` 内置受 `-Dfreej2me.diag.tint`（按顶点数染纯色，忽略纹理）和 `-Dfreej2me.diag.render`（打印渲染调用栈 / transform / mesh identity）控制的诊断。
- `MiniJvmGraphics3DFactory` 受 `-Dfreej2me.m3g.diag.leak=1` 控制：当离屏 FBO 句柄异常失效（绑定落到默认窗口 0）而整帧回退软件渲染时打印一条 `FBO bind FAILED` 提示。正常情况下不应出现。

## 本轮修复：miniJVM GL 后端“游戏帧闪现在 EmuForm 左下方向键区”

### 现象
- 3D 游戏（如 Fast & Furious 6 3D）在 `freej2me + miniJVM` 下运行时，EmuForm 左下角方向键区会**间断性闪现一整张游戏 3D 帧**，频率不固定。
- 拖动游戏 GFrame 到屏幕其它位置，闪烁仍固定出现在左下角。
- 2D J2ME 游戏不出现；纯软件渲染（不走 GL 后端）也不出现。

### 根因
`miniJVM/extlib/xgui` 的 `GLFrameBuffer` 有一个 **finalize 双重释放** bug，在 3D 管线于运行期改变视口而重建 FBO 时触发：

1. `MiniJvmGraphics3DFactory.ensureInitialized` 在视口变化（如菜单 240×320 → 游戏 240×277）时调用旧 FBO 的 `delete()` 释放其 GL 句柄（fbo / rendertex / depth），再 `new GLFrameBuffer(...).gl_init()` 申请新 FBO。GL 驱动**会复用刚释放的 id**，于是新 FBO 拿到的 id 可能与旧 FBO 完全相同。
2. 旧 `GLFrameBuffer` 对象随后被 GC 回收，其 `finalize()` 又排队一个 `Cleaner`，用**旧的（已被复用的）id** 再次 `glDeleteFramebuffers` / `glDeleteTextures`，把刚分配的新 FBO 连同纹理一起删掉。
3. 此后每帧 `frameBuffer.begin()` 绑定的是一个已不存在的 FBO，GL 回退到默认窗口 framebuffer（`GL_FRAMEBUFFER_BINDING == 0`）；而 3D 管线的 `glViewport(0,0,240,277)` 在桌面 GL 里原点 `(0,0)` 就是**窗口左下角**，于是整张游戏帧被画到左下角 240×277 区域，正好压在方向键上。
4. 之所以“间断、不固定频率”：取决于 GC 何时回收旧 FBO 对象并执行 finalize；2D 游戏/软件渲染不重建 FBO，故不触发。

### 定位手段（已沉淀）
- `MiniJvmGraphics3DFactory` 加逐帧诊断（`-Dfreej2me.m3g.diag.leak=1`）打印 `afterBegin fboBind=` / `afterEnd+restore fboBind=` / `readBack fboBind=`。
- 运行日志直接证实：视口从 240×320 切到 240×277 后出现一行 `delete fbo success`（来自 finalize 的 Cleaner），随后所有帧 `fboBind=0` 永久失败、整帧回退软件渲染。
- 另在 `Canvas.paint` 的 `GToolkit.drawImage` 设断点确认 `getX()=225/getY()=32`（GFrame 位置），证明左下角闪现的内容**不是** Canvas 画的，而是 3D 管线画到了窗口。

### 修复
根因修复在 `miniJVM/extlib/xgui`：
- `GLFrameBuffer.delete()` 释放后把 `fbo[0]/rendertex[0]/depth_stencil_buffer[0]` 清零；`finalize()` 在三个句柄均为 0 时直接 return，不再排队清理。
- 同一模式的同类修复（显式 delete/cleanUp 后清零句柄或加“已清理”标志，finalize 跳过重复清理）：
  - `GLShadowMapping`（fbo + rendertex）
  - g3d `ShaderProgram`（programID）、`Loader`（cleanedUp 标志 + `deleteTexture` 同步移除跟踪）、`RenderEngine`（cleanedUp 标志 + `onScreenReSize` 先 delete 旧 mainFbo）
  - xgui `ImageMutable` / `ImageImmutable`（finalize 删除 nanovg 纹理后置位，避免二次 finalize 误删复用 id）

防御性兜底在 `MiniJvmGraphics3DFactory.renderFrame`：
- `frameBuffer.begin()` 之后校验 `GL_FRAMEBUFFER_BINDING != 0`；万一 FBO 句柄再次异常失效，立即整帧回退软件渲染（抛异常由 `releaseTarget` 捕获走 `replaySoftware()`），宁可降速也不把 3D 帧画到屏幕。

### 顺带清理
- `Graphics3D` 里原本无条件的 `[M3G][Background] skip image render` 系列日志改为只在 `-Dfreej2me.diag.render` 时输出（其中 `background image is null` 属正常情况，直接静默）。
- `Graphics3D` 的 `freej2me.diag.render` / `freej2me.diag.tint` 内联判断统一收敛为 `diagRenderEnabled()` / `diagTintEnabled()`。
- `MiniJvmGraphics3DFactory` 移除本轮定位用的逐帧诊断打印，保留 FBO 失效兜底与受属性控制的 `diagLog`。
